# 任务表与窄道调度

Fox WSL调度面板和 OpenRMF 自定义网页共用中央 `/state`、`/command`，任务与路权由同一个 Missions/Traffic 实例管理；不是前端各自判断放行，也不是新增第二个控制器。车辆仍通过广播发现，车端沿用独立 FLEET 租约、Nav2与安全输出。

任务表列为 title、car、pose、init_pose、target_pose、advantage、time、action、loca_advantage。本次按 advantage=任务优先级、loca_advantage=局部路权优先级实现；数值0～100，越大越优先，同级按提交顺序，已获路权者不被抢占。time为最早开始时间，空值立即。任务标题和调度参数按物理身份保存，修改前缀不丢失。

## 使用

1. 各车定位和共享地图配准有效，结束任务并停稳。
2. 标定实际走廊A/B两端中心与宽度，坐标属于fleet_map。也可用所选车当前位置填端点。入口等待点在端部外自动保留0.45m车体余量和0.5m等待间隔；这些点仍须通过本车规划，没有假定现场一定有等待空间。
3. 选择车辆、通道、A→B或B→A；可调用到入口等待点，或明确排队通行到另一端。通行任务包含入口等待点、A/B两端和出口等待点四个检查点。
4. 普通单点/多点任务也检查实际Nav2预检路径经过的通道；全部所需资源一次取得。等待者保留在当前安全位置，不在未获路权时自动驶向对面。
5. 整个任务保守持有资源，直到任务停止/完成得到确认、最新轮速为零且车体离开区域。取消、掉线或进程重启不等于通道清空。持有者在通道内停止时，须先让它退出，其他车继续等待。

配置通道时禁止修改仍占用的区域；两个前端并发编辑有版本检查。参考定位会话变化后停止调度并要求重新标定；“现场确认通道清空/重绑定地图”仍要求全部车定位有效、停稳、结束任务且在通道保护范围外，旧任务不会恢复。

## 边界

- 本实现是现用Humble自定义调度链上的互斥资源管理，并未把这些任意地图航点任务注册为原生RMF交通协商参与者。RMF Schedule在线和RMF原生路权验收是不同的状态。
- 官方Iron/Rolling引入了原生mutex group概念，详见 https://discourse.openrobotics.org/t/new-release-of-open-rmf-on-iron-and-rolling/35397 。当前采用兼容的中央准入方式，不冒充原生mutex API。
- 通道保护是对WSL合作调度任务的准入和实时占用监测，不是硬件防撞装置或Nav2禁行层。车端运行中重新规划可能偏离预检路线，若未获路权车辆进入保护区域，中央请求停止相关调度车辆；通信、定位和制动均有延迟。
- 本地/人工导航不属于中央任务仲裁，必须遵守通道规则；检测侵入时停止相关调度车辆。Nav2实时避障和车端保护仍须有效，未修改用户车体/膨胀/碰撞参数。
- 配置互斥通道后，暂不允许启动编队或连续跟随，通道逐车通行；编队车宽和全队释放条件尚未做通道验收。删除通道配置后可恢复原有模式。
- 整任务持有比逐段释放更保守，吞吐量较低。没有空间让行、目标互占或持续高优先级工作负载时，可能需要操作者调整任务/优先级；不自动倒车抢道。

持久数据在 `data/missions/traffic.json`，包含定义、参考地图绑定、版本、资源持有和任务默认参数；活动任务仍不自动恢复。保存配置/参数不发车，traffic_call是操作者明确发起的运动任务。
